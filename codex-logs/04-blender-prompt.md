Deliver:
1. tools/blender/common.py: asserts bpy.app.version == (4,5,14) (exit non-zero otherwise), argv parsing after `--`, scene reset, deterministic settings (fixed seed, no denoise randomness), helpers to load the camera-pose JSON from DESIGN 7.6 (create tests/goldens/poses.json compatible loader: read the existing file to see its shape, do not edit it), EEVEE render at 1024x768 with the sun/ambient setup of DESIGN 7.2, and a glTF export helper (GLB, +Y up, metres, no draco, materials as unlit/lambert-compatible base colour + texture only).
2. tools/blender/kit_v0.py: generates a placeholder "block kit v0": one mesh per block type of DESIGN 2.2 (1 m cube variants, stairs, ladder, door, walkway, magazine, palace block, weapon mounts, etc. as listed there) with flat vertex colours/simple textures, exported to assets/kit-v0/<block>.glb, plus a 256 px thumbnail per block in assets/kit-v0/thumbs/. Keep polys low (<200 tris per block). This is a stand-in until the ripped originals inform the real skins.
3. tools/blender/turntable.py: given an OBJ (+MTL/texture) path and an output dir, renders a 4-view turntable PNG strip (front/left/back/top, orthographic, consistent scale with a 1 m reference cube and printed bounding-box dimensions in metres in the filename or a sidecar JSON). Intended for ripped originals in assets-ripped/ (reference only; outputs go to assets-ripped/turntables/). If scripts/rip/ has produced OBJs by the time you get there (`ls assets-ripped/`), run it on palast, MauerKlein, MauerGross, TurmKlein, TurmGross, Burgtor, Kanone, Katapult (or whatever names exist) and write assets-ripped/turntables/INVENTORY.md with measured dimensions; if nothing is ripped yet, run it on your kit-v0 meshes to prove it works and say so.
4. tools/blender/validate_glb.py (host python, `python3 -I`): parses GLB header/JSON chunk, checks every mesh has POSITION/NORMAL/TEXCOORD_0, bounds within expected metres, no draco; run it on all kit-v0 GLBs.
5. tools/blender/README.md: how to run each script, Blender version pin, conventions (units, axes, naming `<block>.glb`, damage-state suffixes `_z0.._z3` per DESIGN 2.4).
Common bpy 4.x pitfalls to avoid: use the data API over bpy.ops where possible; when ops are needed use `bpy.context.temp_override`; EEVEE engine id in 4.5 is 'BLENDER_EEVEE_NEXT' (verify with `bpy.types.RenderSettings.bl_rna.properties['engine'].enum_items`); glTF exporter option names changed across versions, read `bpy.ops.export_scene.gltf.get_rna_type().properties` to pick valid ones.
