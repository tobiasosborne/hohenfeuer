## 0. Headline finding: the brief's mental model of the game is wrong

The screenshots show that the 2001 Ascaron game is NOT a fixed isometric two-castle duel and NOT a single pre-rendered image. It is a **real-time 3D, Rampart-like RTS/artillery hybrid** with a free, rotatable, zoomable camera (compass widget in every in-game shot, N/O/S/W labels rotate between shots), a build menu (Kleiner Turm, Kleine Mauer, Goetterstatue, Magierturm, Universalgenie, Windmuehle, Schatzkammer, Munitionsfabrik, Waffenschmiede, Steinmetz, Schaenke, Bauernhaus), gold / population / weapon counters, minimap, magic spells (rain, sandstorm), research (Universalgenie unlocks weapons), per-queen special weapons (Hoellenorgel, Trebuchet, Zeppelin bomber), up to 4 teams, campaigns per queen (Wald, Wueste, Eis, Vulkan), tutorial of 11 steps. A press summary calls it "based on the idea of Rampart" (gry-online via search; MobyGames/myAbandonware list it as real-time artillery strategy in a 3D environment). [verified via screenshots + search]

Consequences for the plan:
- "Classic view" = the free orbit/tilt RTS camera (about 35-50 deg down-pitch, perspective, not orthographic). An orthographic camera will NOT match the screenshots. Use a perspective camera, vertical FOV roughly 45-55 deg (estimate; calibrate against shots 03/07/10).
- Assets are **real-time low-poly textured meshes** (visible hard polygon edges on the cannon, zeppelin, tower caps), not Maya/3ds "pre-rendered sprites". Only menus, scroll/parchment screens and intro videos are pre-rendered (shots 01, 02, 13, 14, 15, 17, 18, 19, 20, 21).
- A first-person view already half-exists in the original: the weapon view (shot 04: behind-the-cannon camera with aim dials, shot 12: trebuchet impact camera with crosshair, shot 08/09: zeppelin flight/target view). So the "first-person option" is a natural extension of the "Waffenansicht" (weapon view).
- Kruse's 1987 Ballerburg (the only open-source prior art) is a different, turn-based 2D side-view game. It is a ballistics reference, not a spec for this game.

## 2. Prior art

### 2.1 Ballerburg SDL (Eckhard Kruse 1987, Thomas Huth port)
- Project page: http://baller.tuxfamily.org/ (moved to baller.frama.io; Emscripten browser build offered) [verified]. Repo cloned: https://framagit.org/baller/ballerburg.git [verified].
- License: **GPL-3.0** for the SDL port (COPYING.txt, file headers "Copyright (C) 1987, 1989 Eckhard Kruse, 2010, 2013 Thomas Huth") [verified]. Kruse's own 2004 source release is described as public domain (Wikipedia https://en.wikipedia.org/wiki/Ballerburg) [verified]. Implication: reading it as a spec is fine; copying code into a non-GPL project is not. Re-implementing the equations (below) from scratch is fine (formulas are not copyrightable expression, but keep your own code).
- Language: C (SDL; 7250 lines incl. GUI). Game logic in src/baller1.c (turn loop, economy) and src/baller2.c (shot flight, damage). Files are ISO-8859-1 with German identifiers.
- Encoded mechanics (units are pixels on a 640x400 playfield, time step per loop iteration):
  - Gravity G = 0.02 per step (src/baller1.h "g/500").
  - Muzzle velocity: v = 0.4 + 0.25 * powder; vx = v*cos(angle)*facing, vy = v*sin(angle); angle 0..180 deg (step 10 or 1), powder 0..99 shown, step 3 or 1.
  - Each step: x += vx; y -= vy; vy -= G; vx += (wind/2 - vx)/5000  (wind acts as a drag toward wind/2).
  - Wind init rand()%60-30; per turn wind = wind*9/10 + rand()%12 - 6 (mean-reverting random walk). The shown wind vane length derives from |wind|.
  - Hit tests: terrain/castle bitmap pixel collision around the ball; on impact, 4 expanding explosion steps test hits against (a) cannons (box), (b) gunpowder/flag-pole/king/storage objects, (c) derricks (30x37 box, 2 radii), (d) windvane, (e) king box (win), (f) building rooms: treasury loses up to 200 gold, powder store empties, cannonball store loses up to 2 balls.
  - Economy (src/baller1.c rechnen): income per turn = people * (tax-function of rate) / (150 - rand()%50), people change per turn with morale (rate 20-ish default), derricks give 40-70 gold each; market prices (6 items: 200,500,400,150,50,50 start) random-walk within min/max bands.
  - AI: 7 computer opponent levels (COMP_NUM 7) in baller1.c; useful as a target-selection reference.
- Is it a usable spec? For the ballistic model, wind drag and damage categories, yes (clean, small). It is NOT a spec for the 2001 game (real-time, 3D, RTS buildings, magic). Treat as inspiration for the "feel" of wind/gravity only; the 2001 game's numbers must be read off the tutorial/UI (e.g. dial "angle / power" values seen in shots 04 and 12) and tuned by feel.
- Other ports listed on the project page [verified]: Ballerr (Ruby clone), Ballerburg OS X, an X11-Basic reimplementation, iOS port (2012, per Wikipedia). I found **no** three.js, Unity, Godot or Ballerburg-3D remake in the searches (two web searches). [verified negative, not exhaustive]
- Do not confuse: MobyGames lists multiple games named Ballerburg; PS1 port "Castle Chaos" 2003 (Phoenix Games) is the Ascaron game (psxdatacenter.com/games/U/B/SLUS-01568.html) [from search results].

## 3. three.js technique survey

Version target: three r160+ (ES modules, `three/addons/...` import path). Docs root: https://threejs.org/docs/ and examples https://threejs.org/examples/.

### 3.1 Cameras: RTS "classic" camera + first-person coexisting
- Classic view = `PerspectiveCamera` on an orbit rig (target point, yaw, pitch 25-70 deg, distance), RTS-style pan/zoom; write your own small controller (about 80 lines) rather than OrbitControls so that you can clamp pitch/target to the map and add edge-scroll/keys. `OrbitControls` is fine for a prototype: https://threejs.org/docs/#examples/en/controls/OrbitControls [unverified fetch, long-standing API].
- First-person: `PointerLockControls` https://threejs.org/docs/#examples/en/controls/PointerLockControls and example https://threejs.org/examples/#misc_controls_pointerlock (page fetch returned only header; API from docs knowledge: `new PointerLockControls(camera, domElement)`, `lock()`/`unlock()` events, `moveForward/moveRight`) [partly verified].
- Coexistence pattern: keep ONE active camera variable and two controller objects; enable only one at a time (`orbit.enabled=false` while locked); on switch, copy pose (FP eye = nearest standable point on castle wall/walkway; classic target = FP position projected). Do not run both controls with the same listeners. Pointer lock requires a user gesture (click/key) and the Escape key always unlocks: design the HUD so Esc returns to the classic view. Pointer lock is not available in headless screenshot tests, so drive FP camera from a deterministic debug API (`window.__game.setCamera({...})`) for goldens.
- The original already has per-weapon cameras (shot 04). Implement FP as "possess a cannon / walk the wall": camera height ~1.6 units at world scale where a castle wall is ~6 units, use `clampStep` on the navmesh to keep the player on the walkways [see 3.3].

### 3.2 "2001 look"
Because the original is real-time 3D at 1024x768 with bilinear textures, the cheapest faithful look is NOT heavy pixelation:
- Render at the original's logical size (1024x768 minus HUD, or scale to the viewport but keep a 4:3 letterbox), no MSAA or low MSAA, mipmapped bilinear textures with 256-512 px textures, vertex-lit/baked lighting, 1 directional light + hemisphere ambient, blob/projected shadows. Use `MeshLambertMaterial`/`MeshBasicMaterial` with baked lightmaps instead of PBR; set `renderer.outputColorSpace = SRGBColorSpace`, `toneMapping = NoToneMapping` to avoid a "modern" look.
- Low-res + nearest upscale (only if you want chunkier pixels): render into a small `WebGLRenderTarget` with `NearestFilter` min/mag, then draw a full-screen quad to the canvas (recipe from the webglfundamentals Q&A https://webglfundamentals.org/webgl/lessons/webgl-qna-how-to-get-pixelize-effect-in-webgl-.html [from search]). three also ships `RenderPixelatedPass` https://threejs.org/docs/pages/RenderPixelatedPass.html (default depthEdgeStrength 0.4, normalEdgeStrength 0.3; adds outlines, which the original does not have, so likely not wanted) [verified via search]. A forum thread notes version mismatch pitfalls with pixel passes (https://discourse.threejs.org/t/pixelation-postprocessing-issues-render-order-and-official-example/86498).
- Palette/dither post: only if the target is the 16-bit-colour look; screenshots show full 24-bit gradients, so skip palette quantisation. A light 5-6-5 quantise + ordered dither shader is optional polish.
- Baked lighting: bake AO/shadow in Blender (Cycles bake to a second UV set or vertex colours), export with glTF, and in three use `aoMap` (uv1) or vertex colours multiplied in a Lambert material. Large cast shadows (towers in shot 16) can use one directional `DirectionalLight` with a 2048 shadow map restricted to the castle bounds.
- NPCs: billboard sprites (cheap, but need 8-direction frames from Blender renders; the original never shows them so you have free hand) vs skinned low-poly meshes (`SkinnedMesh` + `AnimationMixer`, clone with `SkeletonUtils.clone`, https://threejs.org/docs/#examples/en/utils/SkeletonUtils). Recommendation: 150-300 triangle skinned characters with a 2-clip set (idle, run) and `InstancedMesh`/vertex-animation-texture only if you need >100 simultaneous. At RTS zoom a character is ~10 px tall, so even a 4-direction billboard would pass; FP view needs real meshes.

### 3.3 NPC movement
- three-pathfinding (MIT; https://github.com/donmccurdy/three-pathfinding) [verified]: build a navmesh in Blender (separate mesh per zone), export glTF, `Pathfinding.createZone(geometry)`, `setZoneData`, `getRandomNode`, `findPath`, `clampStep` (also for FP walking). It does not build navmeshes itself. Good fit because we already author in Blender.
- Yuka (MIT; https://github.com/Mugen87/yuka) [verified]: steering behaviours (wander, arrive, separation, obstacle avoidance), navmesh, FSM/goal-driven AI; engine-agnostic (needs glue to three). Good for crowds that need collision avoidance; heavier.
- Hand-rolled waypoint graph: for a 2-castle map with perhaps 10-30 NPCs, a graph of 30-60 hand-placed nodes (courtyard, gate, walls, stairs) + A* is simplest, deterministic (seeded RNG) and trivial to keep fixed for screenshot tests. Recommendation: waypoint graph first (placed as empties in Blender and exported in glTF extras), three-pathfinding only if FP free-walking needs navmesh clamping.
- Determinism: all NPC behaviour from a seeded PRNG and a fixed timestep (e.g. 1/60) so golden screenshots are reproducible.

### 3.4 Ballistics, wind, destruction
- Projectile: fixed-step integration, semi-implicit Euler like Kruse's: `v += (wind_vec - v) * k` per step (drag toward wind) and `v.y -= g*dt`. Use fixed 60 Hz sub-steps; for hit detection use swept ray vs castle colliders (raycast along segment per step) to avoid tunnelling at high power. Kruse's constants are a starting point for "feel" only (pixel units).
- Destruction options:
  1. **Pre-authored damage states** per building/wall segment (intact / damaged / rubble swap of a glTF mesh, plus a decal/char texture as in shot 17's blackened towers). Matches the original (buildings have a percentage health, e.g. "Palast (94%)"; collapsing building with dust in shot 09). Cheapest, deterministic, art-directable, and best for the Blender pipeline. Recommended.
  2. Brick/voxel destruction (instanced bricks with physics: cannon.js / rapier). Looks great but costs frame time, non-deterministic, hard to validate against stills. Use only as a cosmetic "debris burst" (30-60 instanced bricks, simple ballistic arcs, no collisions) on top of option 1.
  3. Walls modelled as modular stones with health per stone: middle path (a wall = 6-10 segments; each segment has 3 states). Use this for walls.
- Particles: smoke/fire as camera-facing sprites (`Points` or instanced quads, additive blend for fire/explosion as in shot 17, normal blend for smoke).

### 3.5 glTF from Blender
- `GLTFLoader` (https://threejs.org/docs/#examples/en/loaders/GLTFLoader), add `DRACOLoader`/`KTX2Loader` only if sizes demand. Export `.glb` with Y-up, apply modifiers, Principled BSDF only (other shader nodes are dropped by the Blender exporter); name objects for lookups (`Wall_L_03`, `NavMesh`, `Spawn_*`, `Waypoint_*`). Export animations as NLA tracks/actions with clear names ("Idle", "Run"). Textures: pack PNG/JPEG, 512 px max, power-of-two. [Blender manual glTF page https://docs.blender.org/manual/en/latest/addons/import_export/scene_gltf2.html returned 404 at the time of this research; content from background knowledge; unverified]
- Validate with the Khronos glTF-Validator (https://github.com/KhronosGroup/glTF-Validator [unverified]) in CI before loading in the browser.

### 3.6 Deterministic headless screenshots (Playwright)
- Playwright's `toHaveScreenshot` uses pixelmatch; options verified: `threshold` (0..1, default 0.2, YIQ), `maxDiffPixels`, `maxDiffPixelRatio`, `animations: 'disabled'`, `mask`, `stylePath`, `scale: 'css'` (https://playwright.dev/docs/test-snapshots, https://playwright.dev/docs/api/class-pageassertions) [verified]. Docs advise generating baselines in the same environment that runs the tests (OS/browser/hardware differences).
- WebGL in headless Chromium: software GL via SwiftShader works headless; commonly used flags `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader`; avoid `--disable-gpu` (breaks WebGL on Chrome 130+ per a Playwright-related commit) [from search results, medium confidence; sources: https://www.createit.com/?p=3319, https://chromium.googlesource.com/chromium/src.git/+/d99a9664c873fc38e226e33bc92da974fb852da3]. Confirm with `WEBGL_debug_renderer_info`. SwiftShader output is deterministic on a given build and machine class but differs from GPU output in AA/filtering; so **always capture goldens with the same SwiftShader path**, never mix with GPU.
- Determinism checklist: `?seed=1234&t=fixed` URL params; replace `requestAnimationFrame`/clock with a manual `window.__game.step(n)` then `renderer.render()`; `preserveDrawingBuffer: true` or call `canvas.toDataURL` right after render; disable antialiasing or fix MSAA samples=0; fixed viewport (1024x768) and `deviceScaleFactor: 1`; wait for `window.__ready` after all assets/decoding; avoid `Date.now()`/`Math.random()` (seeded PRNG); disable CSS transitions; fixed camera poses taken from the reference shot. Use the page's canvas `toDataURL` PNG instead of whole-page screenshot to avoid HUD DOM variance.
- Playwright is present on this machine as a global `@playwright/cli@0.1.1`; Node v24.11.1; **Blender is NOT installed** (`blender: command not found`). The Blender install must be added before the asset pipeline can run.

## 4. Blender automation

- Headless: `blender -b file.blend --python script.py -- <args>` (arguments after `--` are ignored by Blender and read via `sys.argv[sys.argv.index('--')+1:]`); use `--python-exit-code 1` so failures produce non-zero exit; `-E CYCLES|BLENDER_EEVEE` selects engine; `-o //out_####` + `-f 1` or `-a` render; order matters (file and `-b` first). [CLI doc page https://docs.blender.org/manual/en/latest/advanced/command_line/arguments.html fetched but content truncated to nav; stated from background knowledge, unverified]
- Docs now at **Blender 5.2 LTS** ("latest") [verified]. Version drift is the main trap for LLM-written bpy:
  - 5.0: `BLENDER_EEVEE_NEXT` renamed back to `BLENDER_EEVEE`; `scene.node_tree` removed (use `scene.compositing_node_group`); `scene.use_nodes` deprecated (always True); legacy Action API removed (`action.fcurves` etc.; use channelbags/slots); BGL removed; render pass names changed ("DiffCol" -> "Diffuse Color", "Z" -> "Depth"); bpy.props no longer accessible via dict syntax; `scene.eevee.gtao_distance` moved to the view layer. [verified: https://developer.blender.org/docs/release_notes/5.0/python_api/ and https://developer.blender.org/docs/release_notes/5.0/eevee/]
  - Earlier: 4.2 introduced EEVEE-Next (`BLENDER_EEVEE_NEXT`), 4.0 changed Principled BSDF input names (e.g. "Specular" -> "Specular IOR Level", "Emission" -> "Emission Color", "Transmission" -> "Transmission Weight") and 4.0 removed the per-object `bpy.context.object.data.use_auto_smooth` (4.1 removed auto-smooth; use Shade Auto Smooth modifier / `shade_smooth` + `mesh.set_sharp_from_angle`); 2.8+ requires `context.view_layer.objects.active`, `obj.select_set(True)`, collections link via `bpy.context.collection.objects.link`; `bpy.ops.*` with context overrides: since 3.2 use `with bpy.context.temp_override(window=..., area=...)` instead of passing a dict (old override dict removed in 4.0). [4.x items from background knowledge, unverified here]
  - Practical mitigation: **pin one Blender version** (e.g. 4.5 LTS or 5.x) and tell the agent the exact version in every prompt; at script start print `bpy.app.version_string` and assert; prefer data-API (`bpy.data.objects.new`, `bmesh`) over `bpy.ops` where possible (ops depend on context and fail in `-b`); never call UI ops (view3d) headless; wrap each build step in try/except that prints a clear traceback; run a lint pass that greps for banned names (`BLENDER_EEVEE_NEXT` when on 5.x, `use_auto_smooth`, `scene.node_tree`, `bgl`).
  - Hallucination guidance article (unofficial): https://www.strayspark.studio/blog/ai-hallucinating-blender-python-api-bpy-fix [search result; not fetched].
- Reference camera matching a perspective RTS view: place a `bpy.data.cameras.new` with `type='PERSP'`, `lens_unit='FOV'`, `angle` = radians(FOV), render 1024x768 with Standard view transform (not Filmic/AgX) and compare against the screenshot. Orthographic (`type='ORTHO'`, `ortho_scale`) is only right for the top-down shot 07, which looks near-orthographic but is a perspective looking straight down.
- Export: `bpy.ops.export_scene.gltf(filepath=..., export_format='GLB', export_apply=True, export_yup=True, export_cameras=False, export_lights=False, export_image_format='AUTO')` (parameter names from background knowledge; check `bpy.ops.export_scene.gltf.get_rna_type().properties.keys()` at runtime because they vary by version).
- Baking: Cycles, `scene.cycles.bake_type='COMBINED'` or `'AO'`/`'SHADOW'`, create a target image node in each material and select it, `bpy.ops.object.bake(type='AO')`; needs a unique non-overlapping UV (Smart UV Project via `bpy.ops.uv.smart_project` requires edit mode; set mode with `bpy.ops.object.mode_set(mode='EDIT')`). Bake at 512 px for a 2001 look. Headless Cycles on CPU works; GPU needs `preferences.addons['cycles'].preferences.compute_device_type`.
- Texture authoring: since the original textures are noisy hand-painted photo-textures (stone, tile, thatch, sand), the agent should generate procedural textures (noise/voronoi/brick nodes) and **bake them to 512 px PNGs**; then compare in the screenshot loop.

## 5. Image comparison for the design loop

The reference is a 2001 JPEG-compressed screenshot (artifacts) of different geometry placement, so strict pixel diffs will always fail; use layered metrics:
1. **Gate 1 - structure and colour (cheap):** downscale both to 128x96, compare colour histograms (chi-square/EMD) and mean colour per 8x6 grid cell; fails fast on wrong palette/layout. Compare using the same crop (3D view only; mask the HUD).
2. **Gate 2 - SSIM** (ssim.js https://github.com/obartra/ssim, or @blazediff/ssim https://jsr.io/@blazediff/ssim [search results]): on grayscale 256x192 crops, mean SSIM; tolerates anti-aliasing/codec noise better than pixel diff. Practical bands (heuristic, my suggestion): <0.5 clearly different, 0.5-0.7 plausible, >0.75 close for different render engines on matching camera.
3. **Gate 3 - pixelmatch/odiff for localisation only:** pixelmatch (ISC; OKLab/HyAB metric with AA detection, `threshold` default 0.1; https://github.com/mapbox/pixelmatch [verified]) or odiff (MIT; YIQ, AA exclusion, `ignoreRegions`, ~6x faster per its own benchmark, supports JPEG/PNG; https://github.com/dmtrKovalenko/odiff [verified]); use threshold 0.2-0.3 and report a diff heatmap, not a pass/fail, because the JPEG source is lossy. For regression of OUR OWN renders (golden vs new), use Playwright `toHaveScreenshot` with `threshold 0.1`, `maxDiffPixelRatio 0.002`.
4. **Perceptual hash (pHash/dHash)**: only a coarse "same scene" check (Hamming distance <10 of 64 bits); useless for fine detail. [unverified lib; implement dHash in ~20 lines].
5. **Vision-model judge:** pass reference crop + candidate crop + diff heatmap to a vision-capable model with a rubric (silhouette, palette, roof colour, stone texture scale, shadow direction, proportion); require a numeric 1-5 score per item and a list of concrete edits ("roof cone 30% taller", "stone courses 2x smaller"). Use metrics as hard gates and the VLM as the editor of what to change. Beware the agent overfitting to a single frame: compare 3+ camera poses per asset (front, oblique, top).
6. Matching the camera is half the work: fit each reference shot's camera (FOV, yaw, pitch, distance) once from the shots and store it in a JSON used by both Blender (turntable renders) and Playwright (browser captures). Compare Blender render to reference first (asset fidelity), then browser capture to Blender render (pipeline fidelity: should be near-identical, SSIM >0.95).

## 6. Recommended architecture (summary)

- three.js (r160+, Vite + TypeScript) single-page game, fixed-timestep deterministic simulation (seeded PRNG) separate from rendering; ECS-lite; game state serialisable.
- Rendering: perspective RTS orbit camera as the "classic" view, with per-weapon behind-the-cannon cameras (as in original) and a first-person walker (PointerLockControls + navmesh `clampStep`) on castle walkways; Lambert/Basic materials with baked AO lightmaps, one shadow-mapped sun, blob shadows, billboard/additive particles, no PBR, no tone mapping; optional nearest-neighbour low-res composer pass kept behind a flag.
- Assets: Blender (pinned version) bpy scripts -> modular kit (wall, tower, keep, houses, cannon, trebuchet, zeppelin, trees, terrain tiles), each with intact/damaged/rubble variants, baked 512 px textures, glTF/GLB export with named empties for waypoints/spawns and a nav mesh; characters 150-300 tris with Idle/Run.
- NPCs: seeded waypoint-graph wanderers (instanced skinned meshes), upgrade to three-pathfinding for FP clamping.
- Combat: Kruse-style integration (gravity + wind drag + swept collisions), pre-authored damage states + cosmetic brick debris, economy/market layered later.
- QA: Playwright + SwiftShader golden screenshots from a debug API with pinned camera poses, layered metrics (histogram -> SSIM -> pixel diff heatmap) plus a vision-model reviewer.

## 7. Top risks
1. **Scope mismatch with the brief**: the 2001 game is a real-time 3D RTS-hybrid, not a two-castle isometric duel; the brief's "keep original gameplay" must be re-specified (tutorial, build menu, research, magic, 4 queens/campaigns, zeppelin) or a conscious scope cut chosen (e.g. only duel + build + 3 weapons). Pixel-perfect match is feasible only for HUD frames and approximate for 3D assets from 21 stills with no texture sources.
2. **AI-driven Blender pipeline fragility and no Blender installed**: bpy API drift (4.x vs 5.x EEVEE id, compositor, Action API), headless context failures, unseen quality of procedural stone/roof textures; needs a pinned Blender, version assertions, linting and a per-asset acceptance test.
3. **Look-validation loop reliability**: lossy JPEG references, different geometry/camera, SwiftShader vs GPU differences and non-determinism make pixel metrics noisy and invite overfitting; need fitted camera JSON per reference shot, SSIM + histogram gates, and goldens captured only on the SwiftShader path.
